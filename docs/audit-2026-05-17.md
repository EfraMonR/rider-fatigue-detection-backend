## 1. Resumen ejecutivo

El backend implementa de forma sustancialmente completa las 5 fases del [plan-001.md](plan-001.md): estructura modular, autenticación JWT + refresh con cookie, ETL CSV/JSON, cifrado AES-GCM, weather + alertas SendGrid, historial paginado, stats, perfil y auditoría. **El proyecto NO está listo para pruebas end-to-end** debido a 4 hallazgos críticos que afectan funcionalmente la API de errores, la clasificación del modelo, el contrato de la respuesta y la posibilidad de levantar el sistema desde un clon limpio.

## 2. Hallazgos críticos

### C-1 · Respuestas de error envueltas en `{"detail": ...}` — viola RF-009
**Evidencia:** [app/api/error_handlers.py](../app/api/error_handlers.py) registra handlers para `FileNotFoundError`, `OperationalError`, `httpx.TimeoutException`, `InvalidTag`, `OSError`, `RequestValidationError` y `Exception`, pero **no para `HTTPException`**. Todos los endpoints lanzan `raise HTTPException(status_code=..., detail={"error_code": "...", "message": "..."})` (ej.: [api_register.py:19](../app/api/auth/api_register.py), [api_upload.py:31](../app/api/analysis/api_upload.py), [api_detail.py:25](../app/api/history/api_detail.py), [api_send.py:26](../app/api/alerts/api_send.py), etc.).
**Impacto:** FastAPI por defecto serializa como `{"detail": {"error_code": "...", "message": "..."}}` en vez del contrato exigido `{"error_code": "...", "message": "..."}`. El frontend i18n (RF-009) busca `error_code` a nivel raíz; todos los endpoints excepto los que pasan por `validation_error_handler` rompen el contrato.
**Severidad:** Critical
**Solución:** Registrar un handler para `starlette.exceptions.HTTPException` que devuelva `JSONResponse(status_code=exc.status_code, content=exc.detail)` cuando `exc.detail` sea dict.

### C-2 · `_cluster_to_stress` asume orden de clústeres no garantizado
**Evidencia:** [inference_engine.py:16-26](../app/models_ai/inference_engine.py) hace `ratio = cluster_label / max(n_clusters - 1, 1)` y mapea por umbrales. El comentario dice "Asume que el modelo devuelve etiquetas 0..n-1 ordenadas por BPM medio ascendente". KMeans **no garantiza ese orden**: las etiquetas dependen de la inicialización aleatoria; sin relabel post-entrenamiento, el clúster 2 puede corresponder a "Low" físicamente.
**Impacto:** Toda la clasificación `stress_level`, `traffic_light` y `verdict` puede estar invertida o aleatorizada respecto al BPM real. Es el núcleo funcional del sistema.
**Severidad:** Critical
**Solución:** En el `model_loader` (o utilidad equivalente), ordenar los centroides al cargar el modelo (`centers = sorted(zip(model[-1].cluster_centers_, range(n)))`) y construir un mapa `cluster_label → stress_index`. Validar al startup que el orden sea coherente con BPM creciente.

### C-3 · `risk_score` con escala invertida para estrés Low
**Evidencia:** [analysis_service.py:63](../app/services/analysis_service.py):
```
risk_score = round(confidence_score * 100, 1) if stress_level == "High" else round(confidence_score * 50, 1)
```
Para `Low` con `confidence_score=1.0` (caso típico, ver C-2), `risk_score = 50.0`. Para `Moderate` con confianza ~0.55, `risk_score ≈ 27.5`. Es decir, **un usuario "Low confianza alta" obtiene mayor `risk_score` que un "Moderate"**.
**Impacto:** Endpoints `/stats/trends`, `/stats/correlations` y `/history/*` exponen un campo numérico fundamental cuyo significado es ilógico. También se usa en `recalculate_profile_status`.
**Severidad:** Critical
**Solución:** Definir explícitamente la escala (ej.: `Low → 0–33`, `Moderate → 34–66`, `High → 67–100`) y derivar `risk_score` a partir de `stress_level` + distancia al centroide.

### C-4 · Modelo `.pkl` excluido del repositorio y de la imagen Docker
**Evidencia:** [.gitignore:222](../.gitignore) contiene `app/models_ai/*.pkl`. El [Dockerfile:10](../Dockerfile) hace `COPY app/ ./app/`, por lo que un build desde un clon limpio **no incluye el modelo** y `model_loader.load_model()` lanzará `ModelNotAvailableError` en cada request.
**Impacto:** El sistema no arranca funcionalmente desde un clon limpio; no hay instrucción en README ni en plan-001 para distribuir el `.pkl`. Bloquea pruebas E2E en cualquier entorno nuevo.
**Severidad:** Critical
**Solución:** (a) Almacenar el modelo en almacenamiento externo (Git LFS, release asset, S3) y documentar la descarga en README; o (b) commit del `.pkl` quitando el patrón del `.gitignore` (1 KB binario, sin secretos).

## 3. Hallazgos importantes (High)

### H-1 · `POST /auth/refresh` está en `protected_router`
**Evidencia:** [routes.py:18](../app/api/routes.py). El router protegido exige `Depends(get_current_user)`, que valida el JWT antes de invocar el handler.
**Impacto:** Cuando el access token expira (401), el flujo definido en RF-010 ("El cliente debe intentar refresh automáticamente") es imposible: el cliente no puede llegar al endpoint sin un access token válido. Contradicción explícita con el ciclo de vida de tokens.
**Severidad:** High
**Solución:** Mover `api_refresh.router` al `public_router`. La autenticación real se hace por la cookie de refresh, no por el JWT.

### H-2 · `profile_status` nunca se recalcula al guardar sesiones
**Evidencia:** [analysis_service.py:65-85](../app/services/analysis_service.py) llama a `create_session`, `save_biometric_series` y `_log_event`, pero no invoca `user_repository.recalculate_profile_status`. Solo [api_calibrate.py:23](../app/api/user/api_calibrate.py) lo dispara.
**Impacto:** RF-007 y Plan §3.8 paso 5 exigen recalcular el estado tras cada sesión exitosa. Un usuario nunca transita `new → calibrating → stable` por uploads; el campo `last_stability_check` queda en `NULL` salvo que el usuario calibre manualmente.
**Severidad:** High
**Solución:** Añadir `user_repository.recalculate_profile_status(user_id)` después de `save_biometric_series` en `process`.

### H-3 · Contrato `confidence_score` inconsistente entre endpoints
**Evidencia:** Spec técnico §3.5 punto 2 y RF-001 dicen "API serializa como entero 0–100". Implementación:
- `/analysis/upload-file` y `/manual-input` retornan **ambos** `confidence_score` (float 0–1) y `confidence_score_pct` (int 0–100) — [analysis_service.py:69-70](../app/services/analysis_service.py).
- `/history/summary` y `/history/{id}` retornan únicamente `confidence_score` (float, del schema REAL).

**Impacto:** El frontend recibe formatos distintos según el endpoint; rompe el contrato declarado en specs y README.
**Severidad:** High
**Solución:** Normalizar: en la capa API exponer siempre el campo como entero 0–100 (calcular al serializar tanto en upload como en history).

### H-4 · `recalculate_profile_status` no cumple la fórmula de RF-007
**Evidencia:** [user_repository.py:79-127](../app/repositories/user_repository.py). Calcula stddev sobre `risk_score` (todos los registros del usuario), sin ventana temporal. RF-007 dice: "stable: ≥ 5 sesiones **y desviación del BPM < 10% en los últimos 7 días**".
**Impacto:** El criterio de estabilidad se calcula sobre la variable equivocada (no BPM) y sin la ventana de 7 días. Combinado con C-3, la varianza de `risk_score` es además ruidosa.
**Severidad:** High
**Solución:** Calcular stddev de `bpm_mean` de las últimas N sesiones en los 7 días previos. Si se opta por mantener risk_score, documentarlo explícitamente y ajustar specs.

### H-5 · `BIOMETRIC_KEY` real en `.env.example`
**Evidencia:** [.env.example:47](../.env.example) contiene `BIOMETRIC_KEY=WeusHENi6YciJN8jgeei6Y98qIGqztS+gXl8oVWjAXY=`.
**Impacto:** Aunque el `.env` real está git-ignored, el `.env.example` SÍ está en el repo (público en GitHub). Cualquier copia que use ese valor por descuido tiene una clave maestra conocida; los biométricos cifrados con ella serían descifrables por cualquiera con acceso al historial git.
**Severidad:** High (en cualquier entorno donde alguien la use por defecto)
**Solución:** Reemplazar por placeholder explícito (`BIOMETRIC_KEY=<generar-con-comando-de-abajo>`) y rotar la clave actual si está siendo usada en alguna instancia.

## 4. Hallazgos medios (Medium)

### M-1 · `init_db` usa `executescript` (solo SQLite)
[main.py:19](../app/main.py) usa `raw_conn.executescript(schema)`. El comentario del spec dice "PostgreSQL: `conn.execute(text(schema))`", pero la promesa de README/spec ("migración a PostgreSQL no requiere modificar código") no se cumple.
**Solución:** detectar dialecto y elegir el método adecuado.

### M-2 · Modelo se carga lazy en la primera request, no al startup
Plan 3.3 exige "Cargar `modelo.pkl` desde `MODEL_PATH` una sola vez al arrancar". [model_loader.py:38](../app/models_ai/model_loader.py) solo carga al primer `get_model()`.
**Impacto:** `/health` retorna 200 aunque el modelo esté ausente; la primera carga puede agregar latencia notable.
**Solución:** invocar `load_model()` en `lifespan` y propagar el fallo como log + degradación documentada.

### M-3 · `/alerts/send` nunca retorna 202 (documentado pero no implementado)
[manual-testing-guide.md:230](manual-testing-guide.md) y spec §3.8.9 mencionan `202 Accepted` para "encolado". [api_send.py:39-57](../app/api/alerts/api_send.py) solo retorna 200 o 503.
**Solución:** eliminar 202 de la documentación o implementar cola real.

### M-4 · `HistoryQueryParams` definido pero no usado
[api_summary.py:15-37](../app/api/history/api_summary.py) declara un modelo Pydantic que luego no inyecta — la validación se duplica inline en el handler. Código muerto que confunde al lector.

### M-5 · `weather_snapshot` siempre persistido aunque la API falle
Cuando el fallback de [weather_service.py:96-103](../app/services/weather_service.py) devuelve `{"warning": True}`, ese dict se guarda como `weather_snapshot` en `analysis_sessions`. El frontend no podrá distinguir "no se consultó" vs "fallo upstream".
**Solución:** marcar `weather_snapshot` con un flag explícito o omitir cuando no haya datos reales.

### M-6 · `tags` del análisis nunca se persisten desde los endpoints
[analysis_service.py:74](../app/services/analysis_service.py) fija `tags: []`. Los endpoints `api_upload.py` y `api_manual.py` no aceptan un parámetro `tags` y no lo pasan a `process()`. RF-007 y README hablan de etiquetar el análisis (Trancón, Lluvia…) y `/history/summary?tags=…` filtra por ellos — pero como nunca se asignan, el filtro siempre vuelve vacío.
**Solución:** aceptar `tags` como input opcional en ambos endpoints, validar contra `user/tags` y propagarlo al INSERT.

## 5. Hallazgos menores (Low)

### L-1 · Logout endpoint requiere JWT válido
[routes.py:19](../app/api/routes.py) lo monta en `protected_router`. Si el access token expiró, el usuario no puede hacer logout (debe esperar a refrescar). UX deficiente.

### L-2 · `verify_password` re-codifica strings ya hasheados
Funcional pero verboso ([auth_service.py:20-21](../app/services/auth_service.py)). No es un bug.

### L-3 · Login revoca **todas** las sesiones del usuario
[api_login.py:33](../app/api/auth/api_login.py). Limita a un único dispositivo por usuario. Alineado con la spec, pero conviene documentarlo en README.

### L-4 · `_REFRESH_COOKIE_MAX_AGE` duplicado en 3 archivos (register/login/refresh)
Constante repetida. Sugerencia: moverla a `auth_service` o `config`.

### L-5 · `analysis_service.process` consume `bpms` antes de validar serie vacía
[analysis_service.py:37-39](../app/services/analysis_service.py) hace `sum(bpms) / len(bpms)` sin verificar. Endpoints validan upstream (`NO_VALID_ROWS`), por lo que el bug nunca dispara, pero el invariante no es defensivo si se cambia el flujo.

## 7. Recomendaciones

1. **Tratar C-1, C-2, C-3, C-4 como bloqueantes** antes de cualquier prueba E2E o demo: rompen el contrato externo (C-1, H-3), la corrección del núcleo de IA (C-2, C-3) y la portabilidad del despliegue (C-4).
2. Una vez resueltos los críticos, abordar H-1 (flujo de refresh) y H-2 (transición de perfil) porque distorsionan los "happy paths" J-001 y J-002 de la spec funcional.
3. Reescribir el handler global de errores como punto único de contrato, registrando `HTTPException` y devolviendo `{error_code, message}` plano. Una vez hecho esto, simplificar los handlers individuales para que devuelvan `JSONResponse(content=...)` o `HTTPException(detail=...)` consistentemente.
4. Agregar una verificación de smoke en `lifespan` que: (a) carga el modelo, (b) valida el orden de clústeres, (c) inserta un audit_log de arranque. Si falla → loggear y dejar `/health` señalizando degradación.
